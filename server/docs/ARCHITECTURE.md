# Бот Proactive — архитектура

Основа — бот ивентов Focused: ивенты, бронь, оплата переводом, билеты, админка и зеркало в Google Таблицу работают так же, как там. Proactive добавляет курсы, заявки, метки источника и мост к таблице задач (разделы ниже отмечены «Proactive»).

## Что делает бот

- **Proactive.** Каталог курсов: карточка с датой старта, расписанием, стоимостью и афишей; тексты на RU / UZ / EN.
- **Proactive.** Заявки на курс или консультацию: имя, телефон, вопрос → карточка в чате продавцов с кнопками статуса.
- **Proactive.** Метки источника в ссылках (`?start=c_3-ig`): запоминаются при первом заходе и попадают в заявки.
- **Proactive.** Мост к статусной таблице задач: регистрация и тестовый режим сотрудников остаются в Apps Script (папка `bot/`).
- **Proactive.** Задачи сотрудников: статусы, приёмка, сводка по отделам и сообщения по RACI прямо из статусной таблицы — [STAFF.md](STAFF.md).
- Показывает опубликованные ивенты: дата, место, карта, цена, сколько мест осталось.
- Бронирует места: выбор типа билета и количества, места держатся `HOLD_MINUTES` (30 мин) на время оплаты.
- Принимает оплату **переводом на карту**: пользователь присылает скрин или PDF чека, чек уходит в чат модерации, модератор жмёт «Одобрить» или «Отклонить».
- После одобрения выдаёт билеты: PNG с QR-кодом и коротким кодом `K7M2-Q9XD`, по одному на каждое место.
- На входе контролёр сканирует QR камерой телефона, бот показывает билет, контролёр жмёт «Впустить». Повторный вход по тому же билету бот не пропустит.
- Админка внутри бота: создание и редактирование ивентов, типы билетов (Standard / VIP…), публикация, выгрузка участников в CSV, рассылка участникам, отмена ивента с возвратами, карта для оплаты, чат модерации, команда (админы и контролёры), статистика.
- Языки интерфейса: RU, UZ (латиница), EN.

## Компоненты

```
Telegram ──polling──▶ aiogram Dispatcher ──▶ handlers ──▶ services ──▶ PostgreSQL
                                │                              ▲
                                └── worker (asyncio-задача) ───┘
                                     • снимает просроченные брони
                                     • перевыдаёт недоставленные билеты
                                     • перепостит чеки, не дошедшие до модерации
                                     • напоминания за 24 ч и 3 ч
Redis — хранилище FSM (шаги диалогов переживают рестарт). Без REDIS_URL — в памяти.

Команды сотрудников ──BridgeMiddleware──▶ веб-приложение Apps Script статусной таблицы (bot/Bridge.gs)
Рассылки команде (дайджест, сроки, статусы) ◀── Apps Script сам, напрямую в Bot API
```

Один процесс, один образ Docker. Вебхуки не нужны, пока нет онлайн-оплаты. Для Click/Payme добавится HTTP-сервер (FastAPI) для callback'ов — см. «Этап 2».

## База данных

```
users ─┬─< orders >── ticket_types >── events
       │     │  └─< payments        (чеки и решения модераторов)
       │     └─< tickets            (по одному на место)
       ├─< notifications            (какие напоминания уже отправлены)
       └─< leads >── courses         (заявки на курсы и консультации)
app_settings                        (карта для оплаты, чаты модерации и заявок, Google Таблица)
```

| Таблица | Ключевые поля | Зачем |
|---|---|---|
| `users` | `tg_id` (unique), `phone`, `lang`, `role` user/staff/admin, `bot_blocked`, `source` | покупатели и команда; `source` — метка первой ссылки |
| `events` | `title`, `description`, `poster_file_id`, `venue`, `address`, `map_url`, `starts_at`, `status` draft/published/cancelled | ивенты |
| `ticket_types` | `price_tiyin`, `capacity`, `reserved` | цена и вместимость; `reserved` = места в бронях + проданные |
| `orders` | `quantity`, `unit_price_tiyin`, `amount_tiyin`, `status`, `seats_held`, `expires_at`, `proof_attempts` | бронь и покупка |
| `payments` | `method`, `status`, `proof_file_id`, `proof_file_unique_id`, `review_chat_id/message_id`, `reviewed_by_*`, `reject_reason`, `external_id`, `raw` | каждый чек (а позже — каждая транзакция Click/Payme) |
| `tickets` | `code` (unique), `token` (unique, секрет QR), `status` valid/used/cancelled, `checked_in_at/by`, `image_file_id`, `delivered_at` | билеты и вход |
| `courses` | `title`, `description`, `schedule` (+ переводы в `i18n`), `starts_on`, `price_tiyin` (NULL — по запросу), `poster_file_id`, `status` draft/published | каталог |
| `leads` | `user_id`, `course_id` (NULL — консультация), `name`, `phone`, `comment`, `lang`, `source`, `status` new/in_work/enrolled/rejected, `manager_*`, `card_chat_id/message_id` | заявки |
| `task_states` | `task_id` (ID задачи из таблицы), `status` (последний увиденный), `accepted_at/by`, `c_notified` | сверка статусов с таблицей и приёмка утверждающим; сами задачи живут в таблице |

Деньги хранятся целыми числами в тийинах (1 сум = 100 тийин) — в том же формате, что ждёт Payme.

### Гарантии на уровне БД

- **Нет овербукинга.** Место захватывается одним условным `UPDATE ticket_types SET reserved = reserved + n WHERE reserved + n <= capacity`; плюс `CHECK (reserved <= capacity)`. Тест: 20 параллельных покупателей на 5 мест — ровно 5 броней.
- **Место не возвращается дважды.** Захват и возврат идут только через `orders.seats_held`.
- **Одна активная бронь на человека и ивент.** Частичный уникальный индекс `(user_id, event_id) WHERE status IN ('pending','under_review')` — двойной тап не создаёт две брони.
- **Чек не одобрится дважды.** Решение модератора берёт `SELECT … FOR UPDATE` на заказ и проверяет статус; второй модератор получит «уже обработан».
- **Одна открытая заявка на человека и курс** (Proactive). Частичный уникальный индекс `(user_id, coalesce(course_id, 0)) WHERE status IN ('new','in_work')`.
- **У заявки один хозяин** (Proactive). «Беру» меняет статус под `SELECT … FOR UPDATE` и только из `new`; второй продавец получит «уже в работе у …».

## Заявки (Proactive)

```
new ──🙋 Беру──▶ in_work ──✅ Записан──▶ enrolled
 │                  └──────❌ Отказ──▶ rejected
 └──✅ / ❌ сразу, без «Беру»
enrolled / rejected ──↩️ Вернуть в работу──▶ in_work
```

Карточка заявки уходит в чат заявок (`app_settings.leads_chat`, запасной вариант — `LEADS_CHAT_ID`), а если его нет или бот не смог туда написать — админам в личку. Кнопки работают у всех участников чата заявок и у админов бота; при смене статуса карточка в чате переписывается. Чат заявок, как и чат модерации, подключает только суперадмин и только закрытый, где он администратор: в карточках телефоны.

## Мост к таблице задач (Proactive)

Статусная Google-таблица (папка `bot/` репозитория) сама рассылает команде задачи по RACI. Входящие сообщения бота читает сервер, поэтому команды сотрудников он пересылает в веб-приложение Apps Script (`bot/Bridge.gs`, `doPost` с общим секретом `BRIDGE_SECRET`):

- `{action: 'staff'}` → `@username` и `chat_id` с листа «Команда», сервер кэширует их на 5 минут;
- `{action: 'message', message}` → прежний `handleMessage_` скрипта; ответ сотруднику скрипт отправляет сам. Если человек не сотрудник, скрипт отвечает `client: true`, и сообщение обрабатывает бот.

Какие команды пересылаются — в README, раздел «Мост к таблице задач». В режиме моста скрипт не опрашивает `getUpdates` (свойство `BRIDGE_MODE`), иначе два читателя отбирали бы друг у друга сообщения.

## Жизненный цикл заказа

```
pending ──чек──▶ under_review ──одобрен──▶ paid ──▶ билеты
   │                  │   └──одобрен, но мест нет──▶ refund_required ──▶ refunded
   │                  └──отклонён──▶ pending (новые 30 мин) │ cancelled (после 3 попыток)
   ├──30 мин без чека──▶ expired ──поздний чек──▶ under_review
   └──отмена пользователем──▶ cancelled
```

Случаи, когда деньги могут «зависнуть», закрыты так:

| Ситуация | Что делает бот |
|---|---|
| Один перевод пытаются засчитать двум заказам (пересохранённый скрин) | У каждого заказа своя сумма: от цены отнимается 1–99 сум (`UNIQUE_AMOUNTS`). Модератор ищет в банке перевод ровно на эту сумму, и один перевод подходит только одному заказу |
| Перевёл на 31-й минуте, бронь уже снята | Чек принимается и для `expired`, бот пробует снова занять место. Не вышло — модератор видит «мест нет», при одобрении заказ уходит в `refund_required` |
| Перевёл, а потом нажал «Отменить бронь» | Чек принимается так же, как для истёкшей брони |
| Прислал чек не через кнопку, а просто фото в чат | Автоматически привязывается только к единственной брони, ждущей оплаты. В остальных случаях бот спрашивает, к какой брони чек |
| Чат модерации не настроен или бот там не админ | Чек уходит админам в личку; если не дошёл никуда, worker повторяет каждые 30 с |
| Сообщение с чеком удалили или сменили чат модерации | «⚙️ Админка → 🧾 Чеки на проверке» берёт список из БД, чек можно отправить заново. Если чек ждёт дольше `REVIEW_ALERT_MINUTES`, админам приходит напоминание |
| Telegram не принял билет (сбой, лимиты) | `tickets.delivered_at` пустой, worker перевыдаёт. Один «застрявший» билет не блокирует остальные; после 10 попыток админам приходит сообщение |
| Тот же файл скрина к разным заказам | Модератор видит «⚠️ этот файл уже присылали к заказу №…» (по `file_unique_id`) |
| Цена изменилась, пока бронь была просрочена | Модератор видит «⚠️ цена изменилась: в заказе X, сейчас Y» |
| Ивент отменён | Брони снимаются, билеты аннулируются, участники получают сообщение. Оплаченные заказы уходят в «💸 Возвраты». Чеки на проверке при одобрении тоже уходят в возврат, при отклонении бронь закрывается окончательно |
| Один человек скупает все места (особенно бесплатные) | Лимит `MAX_TICKETS_PER_ORDER` считается на человека по всем его заказам на ивент |
| Админ-аккаунт угнали и подменили карту | Менять карту, чат модерации и список админов могут только суперадмины из `ADMIN_IDS`. О каждой смене карты сразу узнают все админы и чат модерации, а в карточке чека видны последние 4 цифры карты, которую видел покупатель |

## Роли

| Роль | Как получить | Что может |
|---|---|---|
| суперадмин | `ADMIN_IDS` в `.env` | всё, включая карту для оплаты, чат модерации и назначение админов |
| admin | «👥 Команда → Добавить админа» (только суперадмин) | ивенты, модерация чеков (в т.ч. из лички), возвраты, контролёры, проверка на входе |
| staff (контролёр) | «👥 Команда → Добавить контролёра» | только проверка билетов на входе |
| модератор | быть администратором чата модерации | одобрять и отклонять чеки в этом чате, кроме своих собственных заказов |

Если убрать человека из `ADMIN_IDS`, роль admin в базе у него останется. Снимите её через «👥 Команда».

## Этап 2: онлайн-оплата Click и Payme

Схема уже готова к онлайн-оплате: `payments.method`, `external_id`, `raw`, а заказ одинаково переходит в `paid` и при одобрении модератором, и при подтверждении от платёжки. Что добавится:

1. Способ оплаты `click` / `payme` рядом с `card_transfer`: после подтверждения брони пользователь выбирает, как платить.
2. Адаптер платёжного провайдера: создать платёж в его API, получить ссылку на оплату и отдать её кнопкой.
3. HTTP-эндпоинт (FastAPI) для callback'ов провайдера: проверка подписи, запись события в `payments` (уникальность по `external_id`), перевод заказа в `paid` и выдача билетов той же функцией, что и сейчас.
4. Сверка: worker раз в минуту спрашивает статус платежей, по которым callback не пришёл.
5. Таблица движений денег `money_movements(order_id, kind in/refund, method, amount_tiyin, ref)`. «Нужен возврат» станет вычисляемым: получено − возвращено − использовано > 0. Это же закроет частичные оплаты переводом, которые сейчас не учитываются.
6. Статус `awaiting_provider`: пока транзакция Payme/Click в процессе, бронь не снимается (Payme может завершить оплату через несколько часов). Если оплата пришла после истечения брони, действует то же правило, что и сейчас: занять место заново или вернуть деньги.

### Что нужно узнать у платёжного провайдера

- Создание платежа: endpoint, параметры (сумма, метод click/payme, наш `order_id`, `return_url`), что возвращается (id платежа, ссылка).
- Уведомление об оплате: callback на наш URL (формат, подпись или HMAC, повторы) **или** endpoint статуса для опроса.
- Авторизация: API-ключ или токен, sandbox для тестов.
- Отмена и возврат через API — есть ли.
- Может ли платформа отклонить оплату по истёкшей брони (аналог `CheckPerformTransaction` у Payme), или поздние оплаты остаются на нас — сейчас бот их уже обрабатывает.

Если окажется, что платформа просто даёт доступ к своим кассам Click/Payme, бот можно подключить к ним напрямую по протоколам Click SHOP-API (prepare/complete) и Payme Merchant API (JSON-RPC). Для этого понадобятся отдельный `service_id` / касса с callback-URL на бота.

## Ограничения текущей версии

- Один экземпляр бота (polling). Фоновые задачи уже безопасны для нескольких экземпляров (`SKIP LOCKED`, уникальные ключи), но polling должен идти из одного процесса.
- Курсы не продаются в боте: оплата курса идёт через продавцов, бот ведёт только заявки.
- Тексты ивентов и курсов (название, описание, место или расписание, названия типов билетов) переводит сам админ в форме. Русский текст хранится в обычных колонках, узбекский и английский — в JSONB `i18n`, без перевода показывается русский. Картинка билета рисуется один раз, на языке покупателя на момент выдачи.
- Возвраты делаются вручную; бот только ведёт учёт («нужен возврат» → «возврат сделан»).
